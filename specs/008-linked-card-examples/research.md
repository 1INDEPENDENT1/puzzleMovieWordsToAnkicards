# Research: Связанные слова и все примеры

**Date**: 2026-11-10. Чтение текущего кода и локальной lingua-core; приложение, база и исходники библиотеки не изменялись. Это проектные решения для реализации, не результаты исполнения новых сценариев.

## 1. Идентичность учебной единицы

**Decision**: Отделить стабильную идентичность записи от форм для matching. Канонический ключ слова — хеш полного исходного выражения после Unicode NFC, trim, нормализации пробелов и регистра; не включать перевод или пример. Импорт сохраняет исходное написание отдельно. Начальная форма не служит основанием слияния разных исходных выражений. При совпадении ключа сравнивать полную каноническую строку, исключая молчаливую hash collision.

**Rationale**: Сейчас normalizeSingle использует первый токен, dedupeWords объединяет по нему; `to mince` и `to run` рискуют слиться. contentKey карточки включает перевод и контекст, поэтому изменение примера может породить новую карточку. Полный ключ сохраняет выражение и ручную правку: sourceKey не пересчитывается от пользовательского display override.

**Alternatives considered**: Первый lemma отвергнут; полная lemma-последовательность как ключ хранения тоже может объединить разные исходные единицы. Начальные формы используются только для поиска соответствий. Одинаковые исходные записи одного владельца объединяются с сохранением всех вариантов перевода и происхождения.

## 2. Упорядоченное сопоставление

**Decision**: Для matching слова удалить только начальный служебный префикс `to` у выражения из нескольких токенов или начальный `a/an/the`, затем нормализовать все оставшиеся токены. Одиночные `to`, `a` и т.п. не превращать в пустую запись. Это ограниченное инженерное правило для форм словаря, не удаление стоп-слов вообще. Частицы `up/out/off`, внутренние артикли и повторения сохранять.

Разбить оригинал примера на предложения через BreakIterator(Locale.ENGLISH), затем для каждого предложения вызвать lingua-core.tokenize и lemma для каждого токена. Позиции определять до любых удалений: промежуточные слова считаются все. Нужны ordered occurrences с sentenceIndex/tokenIndex и версией алгоритма. Исходные тексты не заменять леммами.

Для каждой части выражения хранить все достижимые позиции в предложении; переход разрешён при разнице позиций от 1 до 4. Ссылка создаётся один раз, если существует полная цепочка. Это соответствует 0…3 промежуточным словам у каждой соседней пары. Индекс lemma → candidate examples ускоряет поиск; проверка полной цепочки обязательна. Учитывать все повторные вхождения, не выбирать только первое жадно.

**Rationale**: Текущие Set в normalizePhrase теряют порядок и повторы. Часть выражения или совпадение подстроки недостаточны. JDK умеет выделять предложения без новой зависимости; точные границы для сокращений, десятичных чисел, кавычек и `give. Up` должны быть закреплены тестами адаптера, включая нижний регистр после точки. Если JDK ошибочно соединяет очевидные окончания `.!?`, адаптер добавляет разрыв; сокращения и числа не режутся механически по каждой точке. [Java 21 BreakIterator](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/text/BreakIterator.html).

**Alternatives considered**: Unordered lemma-set и любой общий токен отвергнуты. Общая фильтрация служебных слов меняет размер разрыва и разрушает фразовые глаголы. Универсальный NLP parser не требуется согласованным правилом.

## 3. Использование lingua-core

**Decision**: Использовать существующие tokenize/lemma; изменений библиотеки в плане нет. Приведение токена к исходному очищенному виду при невозможности нормализации сохраняется. Нельзя считать неизменившийся lemma доказательством ошибки: библиотека может штатно вернуть исходное слово.

**Rationale**: Локальные Lemmatizer.java, LuceneLemmatizer.java и TextSanitizer.java в соседнем проекте показывают: tokenize сохраняет порядок, lemmas/analyze возвращают Set, lemma не удаляет служебные слова и не распознаёт выражения. Границы предложений нужно получить до tokenization.

**Alternatives considered**: Расширение публичного API библиотеки позициями возможно позднее при доказанной потребности, но для 008 адаптера приложения достаточно.

## 4. Дедупликация и источники примеров

**Decision**: Идентичность примера включает владельца и исходное происхождение. При наличии стабильного source ID использовать его; иначе fallback = хеш нормализованных пробелов оригинала + отдельных исходных переводов + movie URL/title/sourceLabel. Не использовать lemma, страницу или номер строки как идентичность. Два разных фильма сохраняются как разные source occurrences. Исходный source ID и позиция отдельно сохраняются в provenance снимка; одна source occurrence с несколькими ссылками не копируется в карточки.

**Rationale**: Сейчас dedupePhrases объединяет по lemma-text и берёт первый фильм. В проверенных fixtures нет стабильного data-id, хотя парсер умеет его извлекать. Поэтому fallback необходим. При изменении исходного содержимого без стабильного ID новая версия может остаться отдельным примером: это осознанный выбор сохранности против эвристического слияния. Повтор идентичного импорта дублей не создаёт.

**Alternatives considered**: Объединение всех одинаковых lemma-фраз теряет источники; page/row меняются при пагинации. Не создавать отдельную Movie сущность: хватает метаданных примера, запрос управления фильмами отсутствует.

## 5. Долговечность и транзакция импорта

**Decision**: Сохранять VocabularyImportSnapshot для завершённого задания: versioned typed structured records и accepted source fields до lossy dedupe, включая inline examples, переводы, provenance/order, completion warnings. JSONB — транспортный снимок, а опубликованный словарь нормализован по сущностям. Внешний transactional service сохраняет snapshot и статус COMPLETED атомарно после записи файла. При ошибке транзакции удаляется файл по существующему failure path; падение процесса между файлом и commit оставляет только недоступный незавершённый job, не ложный completed.

POST /reviews/cards сохраняется: owner check, completed check, warning-presentation gate, затем транзакционный upsert всего словаря/связей/карточек. В PHRASES импортируются только примеры, которые сопоставляются с уже сохранёнными словами. При новом слове повторно сопоставляются сохранённые фразы. Импорт добавляющий: отсутствие строки не удаляет старые данные.

**Rationale**: generatedData — ConcurrentHashMap процесса; текущее создание карточек невозможно после restart. Простой @Transactional на внутреннем вызове не гарантирует transaction boundary: использовать существующие Spring proxy boundaries явно, не вводить фоновые события для обязательного сохранения. Работа с файлом и SQL не является распределённой атомарной транзакцией; контракт не обещает её.

**Alternatives considered**: Парсинг TSV/HTML back запрещён; постоянный кэш без сохранения не решает restart; автоматическая публикация до предупреждения нарушает flow 007.

## 6. Изоляция и конкурентный импорт

**Decision**: В каждой новой сущности user_id; запросы по id+user. Составные FK (user_id, entry_id/example_id/card_id) ссылаются на UNIQUE(user_id,id), запрещая межпользовательские связи на уровне PostgreSQL. На импорт брать краткую блокировку строки владельца только внутри SQL-транзакции, без HTTP-запросов. Unique constraints защищают повторный импорт. Редактирование — optimistic versions; stale writer получает 409, а не повторное присваивание старого значения.

**Rationale**: Одних проверок Java недостаточно при конкурентных операциях. PostgreSQL поддерживает уникальность групп столбцов и составные foreign keys. [PostgreSQL constraints](https://www.postgresql.org/docs/16/ddl-constraints.html).

**Alternatives considered**: Глобальные shared vocabulary records не соответствуют личным переводам; незащищённый find-then-insert допускает дубли.

## 7. Начать учебную коллекцию с нуля

**Decision**: По последнему решению пользователя не переносить старые карточки, ответы, расписания и правки. Выполнить однократное пересоздание только учебной коллекции и свежий импорт. Одна ReviewCard с обязательным entry_id, обычные прямые ReviewAttempt; без архивов, merge targets, lifecycle, checkpoints и resolution records.

**Rationale**: Перенос пока не нужен пользователю и существенно усложняет задачу. Ранее изученные ограничения старых смешанных переводов больше не требуют решения в этой feature. После первоначального построения новые данные всё равно сохраняются при restart и повторном импорте.

**Alternatives considered**: Прежний дизайн объединения истории и ручного выбора отменён пользователем. Автоматическое удаление на каждом старте или импорте не соответствует однократному началу с нуля.

Для чистой модели использовать JPA creation и штатный Spring SQL initializer после Hibernate (defer-datasource-initialization=true) для дополнительных составных ограничений. Старый compatibility SQL переноса заменяется чистой идемпотентной инициализацией. Отдельные VocabularySchemaInitializer, readiness endpoints и два этапа переноса populated rows не требуются. Последовательность описана в [fresh-start.md](fresh-start.md). Возможность выполнять SQL после создания JPA-схемы подтверждена в [Spring Boot 3.2.5: Database Initialization](https://docs.spring.io/spring-boot/docs/3.2.5/reference/html/howto.html#howto.data-initialization.using-basic-sql-scripts).

## 8. UI, раскрытие и редактирование

**Decision**: Отдельный dialog с постраничным чтением примеров. Review presentation получает случайный идентификатор в HttpSession; reveal основной карточки подтверждается сервером, а выдача перевода примера проверяет этот показ и принадлежность связи. Новая карточка/повторный показ создаёт новый контекст. Это состояние повторения, не изменение аутентификации. Библиотека и явное редактирование собственных данных не являются режимом проверки памяти и не блокируются этим gate.

Ручная правка слова хранится в VocabularyEntry как display override; правка примера из конкретной карточки — на WordExampleLink, чтобы не изменить контекст других слов. Ручное редактирование не меняет source VocabularyExample; импорт по стабильному source ID может обновить source, сохраняя прежний материал в snapshot. При наличии нескольких примеров редактор явно выбирает конкретный; instanceText без идентификатора не изменяет случайный первый пример; обратная совместимость старого редактора не требуется.

**Rationale**: Обычный hidden плюс уже доставленный перевод недостаточен для надёжного запрета преждевременной выдачи через review action. Ручные правки одного контекста не должны неожиданно изменять другой.

**Alternatives considered**: Все переводы примеров в initial JSON отвергнуты. Новая frontend-платформа не нужна. Возможности общего редактора связей не добавляются.

## Результат исследования

Неизвестных, требующих продуктового решения, не осталось. Пользователь явно исключил перенос прежней коллекции; документы описывают чистое построение и сохранность последующих новых данных. Технические наблюдения старого кода в discovery.md остаются справкой о текущем состоянии, а не требованиями совместимости. Дизайн новой модели и контрактов не означает, что приложение уже изменено или протестировано.
